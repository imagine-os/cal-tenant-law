intent: Build the drafting system Justin asked for: California pleading paper as a real editing surface with the relevant laws, the precedent, live recommendations and the client's own details beside the page, and the ability to turn "things to ask the client" into requests the client actually answers in their app. Replace the WordPerfect habit (D-018) with a browser editor that keeps the pleading-line ruler and prints real Letter pages. decision: D-018 (browser editor with a pleading-line ruler and PDF / DOCX export) · D-047 (canonical pipeline stages; every move through applyTransition) · D-051. rejected: Rich-text HTML in drafts.blocks (blocks stay plain text with {{variables}}, so the line grid, pagination, print and a future DOCX export all read the same thing); a live link from a draft to its template (a template edit would rewrite a document already with a court - the draft copies); measuring the DOM for pagination (an estimate of 28 lines a page and ~85 characters a line is the same in the editor, in print and in a screenshot, which is worth more than accuracy that drifts); a `verified` column on precedents that defaults to true (every row ships false, D-019); a second copy of the statute index in a table (the markdown stays the single source of truth and is parsed read-only); a `version` column on `templates` (the base optimistic-concurrency column already owns that name, so template numbering is `template_version`); a separate table for checklist ticks (they ride in drafts.variables._checklist until T-067 needs more); a Placeholder for print (the print stylesheet is real - only DOCX is unwired).
