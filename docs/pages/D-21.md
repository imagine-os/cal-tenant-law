# D-21 · Canvas

## Purpose

Justin asked for "a canvas where we can open all the individual pages and lay them out to see all the working software laid out… zoom in and use any page from the dashboard or mobile experience from a canvas rather than only seeing one page at a time". This is that page: every route in the manifest becomes a frame on one zoomable, pannable surface, grouped into labelled regions per surface family, and each frame is the real page running in a same-origin iframe as the role of its surface — so you can click into the front desk, then the attorney, then the tenant's phone, without leaving the canvas.

## Sections (layout order)

1. PageHeader — title, live-frame counter (`12 live of 24`), page code in dev mode
2. Toolbar — zoom out / level / zoom in, Fit all, group select (fits that group), surface filter, Built only, search, live-frame cap, frame language, frame builder tool
3. Hint row — pan / zoom instructions and the key map; the hint's tooltip explains the per-frame role
4. CanvasViewport — the scrollable surface: dashed labelled regions, frame cards (code, name, built/stub badge, role, Focus, Open) with a live `DeviceFrame` or a "Not loaded / Load this page" card
5. Minimap — region rectangles plus the viewport window (bottom left); point at it to move the view
6. FocusOverlay — one frame enlarged in a `Modal` to a working size, with "Open the full page"
7. ListView — under 700 px (and inside a frame) every page as a list with Open buttons, instead of the surface

## Logic

- **Frames**: `toNodes(getRoutes())` takes one frame per page code (a parameterised path such as `/dev/tables/:table` is filled with a sample value, mirroring `scripts/qa-lib.mjs`).
- **Regions**: surface families in reading order (Public site, Client app, Game board, Front desk, Attorneys, Assistants, Owner, Admin, Opposing counsel, Marketing, Plan, Manual & docs, Dev tools). Inside a region, frames sit in a grid (3 columns for desktop pages, 6 for phones).
- **World**: regions are shelf-packed into a landscape world whose width is `sqrt(area × 1.35 × 2.4)`, so "fit all" is as large as a wide, short viewport allows (today 10 942 × 5 956 world px, ≈ 25 % on a 4K screen, ≈ 9 % on a laptop).
- **Frame role**: the natural role of the surface when the route allows it, else the first allowed role. It reaches the frame through the iframe hash (`#/counsel?as=attorney&dev=0&lang=en&theme=light`) — see "Real vs mock".
- **Zoom / pan**: zoom 0.06 … 1 with the buttons, `+` / `−`, `Ctrl`/`⌘` + wheel (anchored on the pointer), Fit all and Fit group; panning is the viewport's own scroll, so drag, arrow keys, scrollbars, trackpad inertia and the minimap all work. `0` fits everything, `Enter` focuses the last frame you tabbed into, `Esc` closes it.
- **Performance**: an `IntersectionObserver` (root = the viewport, 240 px margin) tracks what is in view; at most `cap` frames (4 / 8 / 12 / 20, default 12) are live, ordered by position, plus the focused one and anything loaded by hand. The rest are "Load this page" cards.
- **Persistence**: `ctl.canvas` keeps zoom, filters, cap, frame language / builder tool and the scroll position.

## Real vs mock

Everything is real: real routes, real pages, real guards, mock data (the frames share the one `ctl.db.v1` database, so a row added in one frame shows in another after a reload).

**Per-frame role without editing a shared file.** `localStorage` is shared by every same-origin frame, so a frame cannot simply write a session. Instead `src/modules/showcase/frameSession.ts` runs at module-evaluation time (the registry globs this module before React renders) and, **inside an iframe only** and **only when the hash carries `as` / `dev` / `lang` / `theme`**, shadows the three keys the providers read (`ctl.session`, `ctl.lang`, `ctl.theme`) with the values from the hash and swallows writes to them. Each window has its own `Storage.prototype`, so the parent window's session is untouched and a frame can never write one back. No edit to `SessionProvider`, `App.tsx`, the shells or the registry.

**No nesting.** The three pages that themselves lay out other pages detect `isFramed()`: the hub shows static preview tiles, the canvas shows its list view, the simulator shows an "open the full page" card. So a canvas inside a canvas is one frame deep, never recursive.

## Inputs and responsive check (P-01, P-03)

Checked at 360, 390, 768, 1280, 1920, 2560, 3840 in light and dark (`npm run qa:responsive`, 0 failing cells): no document-level horizontal scroll at any width — the surface scrolls inside its own container — no console errors, no text under 12 px (16 px at ≥ 1920). Under 700 px the page renders the list view with a "best on a larger screen" note, and the zoom / fit / frame controls are not rendered at all, because in list view they would be controls that do nothing (P-09).

Keyboard: the viewport is focusable and handles arrows, `+`, `−`, `0` and `Enter`; every frame's Focus and Open are native buttons in tab order; the minimap only duplicates what the arrows and the fit buttons already do (P-03: nothing pointer-only, nothing drag-only). The canvas world keeps `--scale: 1` so it is a fixed design surface the viewer zooms, while the page chrome scales with the width band.

Known warning: `npm run qa:responsive` reports `target-size` findings for the Focus / Open buttons on the canvas — they are 44 px in world coordinates but measured after the zoom transform, so at 9 % they are 4 px on screen. That is what zooming out means; the Focus overlay and the list view give full-size targets.

## Resumen en español

El lienzo coloca todas las páginas de CTL OS en una sola superficie con zoom y desplazamiento, agrupadas por superficie, y cada marco es la página real ejecutándose con el rol de su superficie: se puede usar dentro del marco, ampliarla o abrirla.
