# D-22 · Demo simulator

## Purpose

Justin asked for "a really good way to present everything we build in a demo simulator for mobile and for desktop" and, in prompt 0006, for the simulator to "show the demos in the proper device being represented". This is the presenting surface: pick a page and it opens on the device that surface is really used on, drawn as that device - pick another one by hand and it stays pinned until you hand control back. Role, language, light or dark and the builder tool are all switchable, present mode hides the chrome, the Tour walks a scripted sequence, and the address bar carries every choice, so a link reopens the same demo.

**Pass 2 wave A (T-124, D-050).** Two things changed. (1) **Device chrome per preset**: the phone has a rounded bezel, a dynamic island and a home indicator; the tablet a bezel and a camera dot; the laptop a screen bezel, a hinge and a keyboard deck; the monitor a thin bezel with a neck and base; the TV a very thin bezel, two feet and a "10-foot view" caption. The chrome is decoration (`aria-hidden`), it never changes the viewport the page sees, and it is off by default so the hub previews and the canvas are untouched. (2) **The device follows the route**: `customer` -> phone 390, `owner` -> 2560, `public` -> laptop 1280, dev and plan -> laptop 1280, every other staff surface -> 1920. A client-app demo is therefore never shown in a desktop frame by accident, and a device you pin that is a different kind from the route's is badged **Responsive check**, so the demo stays honest.

## Logic

- **Devices**: seven presets — phone 360 / 390, tablet 768, laptop 1280, monitor 1920 / 2560, 4K TV 3840. The iframe really is that wide, so the framed page picks its own `--scale` band and media queries. Each preset names the hardware it is drawn as (`DeviceFrame chrome`): phone, tablet, laptop (≤ 1440), monitor (1920 and 2560), TV (3840, with the "10-foot view" caption). The keys stay `laptop1280` / `desktop1920` / `tv2560` / `tv3840` because they are part of the URL and the actions manifest; only the label and the chrome say what the device is.
- **Auto device (D-050)**: `AUTO_DEVICE` maps the route's surface to a preset (customer → phone 390, owner → 2560, public / dev / plan → laptop 1280, every other staff surface → 1920). Picking a device by hand sets `?pin=1` and it stays through page changes; **Auto** clears it. A pinned device whose kind differs from the route's is labelled **Responsive check**.
- **Sit back**: the stage is capped at `min(100%, the device's own width, (100dvh − chrome) × aspect)`, so a 3840 TV fits the window whole instead of running off the page, and a phone is never blown up past 390.
- **Orientation**: rotate swaps width and height, for phones and tablets only (the button is disabled otherwise, with a tooltip that says so).
- **Role**: choosing a page sets the role to the demo role of its surface; the role select then overrides it. Parameterised paths are filled with the same sample ids the QA scripts use, and two routes that fill to the same address (`/docs` and `/docs/*`) appear once. Role, language, theme and builder tool reach the frame through the iframe hash (`#/app?as=client&dev=0&lang=es&theme=dark`) and are applied **inside the frame only** by `src/modules/showcase/frameSession.ts`, so presenting never changes your own session (see D-21 "Real vs mock").
- **URL**: `?device=&pin=&route=&role=&lang=&theme=&dev=&rot=&present=&step=` — every control writes there (replace, so the back button does not fill up), which is what makes a demo shareable.
- **Tour**: hub (laptop) → the client's orders on phone 390 → the game board → the attorney pipeline on 1920 → the owner on 2560 → the proposal on a laptop. A step whose page is still being built falls back to a named nearest page (`/counsel` for the pipeline, `/app` for the orders) and says so, so the tour never dead-ends while modules are still landing.
- **Present mode**: a full-window layer with just the frame, the page's identity badges, the tour buttons and an exit; the shortcut card shows once and is remembered.
- **Keyboard**: `P` present, `→` / `←` tour steps, `D` cycles the device (and pins it), `R` rotate, `Esc` leave present mode (ignored while typing in a field).

## Real vs mock

Real routes, real guards, real device widths; mock data. The framed page is the same build, so what you present is what ships. The hardware around it is drawn (SVG-free CSS: bezel, island, deck, stand, feet) and never affects the page inside.

## Inputs and responsive check (P-01, P-03)

Checked at 360, 390, 768, 1280, 1920, 2560, 3840 in light and dark (`npm run qa:responsive`, 0 failing cells): no horizontal scroll, no console errors, no text under 12 px (16 px at ≥ 1920). Under 700 px the seven device presets become a Select and the device pill takes the full row. The stage keeps the whole device inside the window at every width (`--sim-room` is the page chrome above and below; present mode leaves almost all of the window to the device).

Keyboard: every control is a native button, select or switch; the shortcuts (`P` `→` `←` `D` `R` `Esc`) are listed on the page and in present mode; the rotate button carries a tooltip that opens on focus and says why it is disabled; nothing is hover-only or drag-only; targets are 44 px.

## Resumen en español

El simulador presenta cualquier página **en el dispositivo en el que se usa de verdad**: la app del cliente en un teléfono 390, el titular en una pantalla de 2560, el sitio público en un portátil, el resto del personal en un monitor de 1920. Cada preajuste se dibuja como su aparato (bisel y notch del teléfono, cámara de la tableta, teclado y bisagra del portátil, pie del monitor, patas y "vista a tres metros" de la TV 4K). Si fijas otro dispositivo a mano, se marca como "prueba de adaptación" para que la demostración sea honesta. La URL lleva todas las opciones, así que un enlace abre la misma demostración.
